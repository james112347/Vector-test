# Phase 1: PWA Shell + Auth + Design System - Research

**Researched:** 2026-02-11
**Domain:** Progressive Web App development with React, authentication, offline-first architecture, neuroscience-based design systems
**Confidence:** HIGH

## Summary

Phase 1 establishes the foundational PWA infrastructure with installability, offline support, password authentication with T&C acceptance, and a neuroscience-informed design system with dark mode. This phase requires careful selection of modern tooling that will support the long-term data tracking and AI features planned for later phases.

The recommended stack combines **Vite + React 19 + TypeScript** for the build system and framework, **vite-plugin-pwa with Workbox** for service worker generation and offline support, **Dexie.js** for offline-first IndexedDB storage, **React Router v7** for authentication routing, **Tailwind CSS + shadcn/ui** for the component system, and **React Context API** for authentication state management. This stack is proven, actively maintained as of 2026, and optimized for PWA development with minimal configuration overhead.

For neuroscience-based colors: **blues and greens** (calming, trust, focus) for rest/recovery states, **warm tones** (oranges, yellows) for energy/alert states, and **pink accents** for stress reduction. Dark mode uses the same principles with reduced luminance.

**Primary recommendation:** Use Vite PWA plugin with generateSW strategy for automatic service worker generation, Dexie.js for persistent offline storage, React Context API for auth state, and shadcn/ui components with custom neuroscience-informed color tokens in Tailwind CSS.

### Pattern 1: Split Auth Context (Performance Best Practice)
**What:** Separate auth state and auth actions into two contexts to prevent unnecessary re-renders
**When to use:** Always for authentication state management
**Example:**
```typescript
// Source: https://thelinuxcode.com/state-management-in-react-2026-hooks-context-api-and-redux-in-practice/
// contexts/AuthContext.tsx

// State context - updates when user/isSignedIn changes
export const AuthStateContext = createContext<AuthState | null>(null);

// Actions context - stable functions, rarely updates
export const AuthActionsContext = createContext<AuthActions | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [isSignedIn, setIsSignedIn] = useState(false);

  // Initialize auth state on app load
  useEffect(() => {
    // Check for existing session in IndexedDB
    checkSession();
  }, []);

  // Stable actions (memoized)
  const actions = useMemo(() => ({
    signIn: async (email: string, password: string) => { /* ... */ },
    signOut: () => { /* ... */ },
    register: async (email: string, password: string) => { /* ... */ }
  }), []);

  return (
    <AuthStateContext.Provider value={{ user, isSignedIn }}>
      <AuthActionsContext.Provider value={actions}>
        {children}
      </AuthActionsContext.Provider>
    </AuthStateContext.Provider>
  );
}
```

### Pattern 3: Dexie.js Database Setup for Offline Auth
**What:** IndexedDB schema for user sessions and persistent login
**When to use:** Store auth tokens and user data offline
**Example:**
```typescript
// Source: https://dexie.org/ + https://blog.logrocket.com/dexie-js-indexeddb-react-apps-offline-data-storage/
// db/db.ts

import Dexie, { Table } from 'dexie';

export interface User {
  id?: number;
  email: string;
  hasAcceptedTerms: boolean;
  termsAcceptedAt?: Date;
  createdAt: Date;
}

export interface Session {
  id?: number;
  userId: number;
  token: string; // Store access token in memory, refresh token here
  expiresAt: Date;
  createdAt: Date;
}

export class VectorDB extends Dexie {
  users!: Table<User>;
  sessions!: Table<Session>;

  constructor() {
    super('VectorDB');
    this.version(1).stores({
      users: '++id, email',
      sessions: '++id, userId, expiresAt',
    });
  }
}

export const db = new VectorDB();

// Important: Request persistent storage to prevent eviction
if (navigator.storage && navigator.storage.persist) {
  navigator.storage.persist().then((persistent) => {
    console.log('Persistent storage:', persistent);
  });
}
```

### Pattern 6: Terms Acceptance Flow (GDPR/Privacy Compliant)
**What:** Clear, affirmative T&C acceptance before registration
**When to use:** Always before completing registration
**Example:**

// components/auth/Register.tsx

export function Register() {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [hasAcceptedTerms, setHasAcceptedTerms] = useState(false);

      <div className="flex items-start gap-2">

          id="terms"
          checked={hasAcceptedTerms}
          onCheckedChange={setHasAcceptedTerms}
        />

          I accept the{' '}
          <a href="/terms" target="_blank" className="underline text-calm-blue">

          </a>
        </label>
      </div>

      <Button type="submit" disabled={!hasAcceptedTerms}>
        Register
      </Button>
    </form>
  );

### Anti-Patterns to Avoid
- **Don't hash passwords in React:** bcrypt belongs on the backend (Node.js server), not in the browser. Hashing client-side gives false security - always send passwords over HTTPS to a secure backend.
- **Don't store refresh tokens in localStorage:** Use secure HttpOnly cookies for refresh tokens, or store access tokens in memory (React state) and refresh tokens in HttpOnly cookies.
- **Don't use Browse-wrap for T&C:** GDPR requires affirmative action (clickwrap). Pre-checked boxes and implied consent are non-compliant.
- **Don't overuse Context for all state:** Context is for auth and environment state (theme, locale). Use useState/useReducer for local state, and consider Zustand/Jotai for complex shared client state.
- **Don't skip persistent storage request:** IndexedDB data can be evicted unless you call `navigator.storage.persist()`. Request it during auth initialization.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Service worker generation | Custom SW scripts with manual caching rules | vite-plugin-pwa + Workbox | Workbox handles cache versioning, precaching, runtime caching, and update strategies automatically. Hand-rolled SWs break on updates. |
| IndexedDB queries | Raw IndexedDB API with transactions | Dexie.js | IndexedDB API is callback-based, verbose, and error-prone. Dexie provides promises, queries, and handles version migrations. |
| Accessible components | Custom modals, dropdowns, tooltips | Radix UI (via shadcn/ui) | Accessibility is hard - keyboard navigation, ARIA attributes, focus trapping. Radix UI handles all of it. |
| Password hashing | Custom crypto in browser | bcrypt on backend | Client-side hashing is pointless security theater. Attackers intercept before hashing. Always hash server-side with bcrypt (12+ rounds). |
| Dark mode toggle | Manual class toggling and localStorage | Tailwind dark mode + useDarkMode hook | Dark mode has edge cases (system preference, persistence, SSR flicker). Tailwind + a simple hook solves it. |
| Protected routes | Manual auth checks in every component | React Router v7 ProtectedRoute pattern | Centralize auth logic. Manual checks lead to bugs and inconsistent behavior. |

**Key insight:** PWAs have deceptively complex edge cases (service worker updates, cache invalidation, offline sync, installability criteria, IndexedDB eviction, auth token refresh). Use proven libraries that handle these edge cases, not custom solutions.

## Common Pitfalls

### Pitfall 1: Service Worker Not Updating
**What goes wrong:** Users stuck on old version after deployment, cached content never refreshes
**Why it happens:** Service worker caches itself aggressively. Browsers check for SW updates on navigation, but only if SW file changes byte-for-byte.
**How to avoid:**
- Use vite-plugin-pwa with `registerType: 'prompt'` to ask users to reload when updates are available
- Set `Cache-Control: no-cache` header for service worker file on hosting platform (Vercel, Netlify auto-configure this)
- Version your service worker file or use Workbox's built-in cache-busting
**Warning signs:** "I deployed but users see old content", "changes don't appear until hard refresh"

### Pitfall 2: IndexedDB Data Eviction
**What goes wrong:** User data deleted by browser during storage pressure, all progress lost
**Why it happens:** IndexedDB is "best-effort" storage by default. Browsers can evict it to free space.
**How to avoid:**
- Call `navigator.storage.persist()` on first login to request persistent storage
- Educate user: "Grant storage permission so we don't lose your data"
- Test: Chrome DevTools > Application > Storage > Check "Simulate custom storage quota"
**Warning signs:** Users report "data disappeared", storage shows 0 bytes after browser restart

### Pitfall 3: Auth Token in localStorage (XSS Vulnerability)
**What goes wrong:** Attacker injects malicious script, reads localStorage, steals auth tokens
**Why it happens:** localStorage is accessible to all JavaScript, including injected scripts (XSS attacks)
**How to avoid:**
- **Short-lived access token in memory** (React state/Context) - lost on refresh, that's fine
- **Long-lived refresh token in HttpOnly cookie** (backend sets, JavaScript can't read)
- If backend not ready: accept risk of localStorage for v1, but flag as tech debt
- Always use HTTPS to prevent token interception
**Warning signs:** Security audit flags localStorage usage, penetration test finds XSS

### Pitfall 4: PWA Not Installable
**What goes wrong:** "Add to Home Screen" prompt never appears on mobile
**Why it happens:** Missing manifest properties, HTTPS not enabled, service worker not registered, or start_url not cacheable
**How to avoid:**
- Use vite-plugin-pwa - auto-generates compliant manifest
- Test with Lighthouse PWA audit (Chrome DevTools)
- Ensure HTTPS (Vercel/Netlify provide free SSL)
- Check manifest has: name, short_name, icons (192x192 + 512x512), start_url, display: "standalone"
- Verify service worker registers successfully
**Warning signs:** Lighthouse shows "Does not register a service worker", manifest errors in DevTools

### Pitfall 5: Dark Mode Flash on Load
**What goes wrong:** Page loads in light mode, then flashes to dark mode after React hydrates
**Why it happens:** Dark mode preference stored in localStorage, but read after React renders
**How to avoid:**
- Inject inline script in index.html `<head>` that checks localStorage and adds `class="dark"` before render
- Or use Tailwind's `dark` variant with `media` strategy: `darkMode: 'media'` (respects system preference, no flash)
- Or use a library like `next-themes` (works with Vite too)
**Warning signs:** Users report "white flash on load in dark mode", theme flicker

### Pitfall 6: T&C Acceptance Dark Patterns
**What goes wrong:** Pre-checked T&C boxes, hard-to-find "Reject" buttons, bundled consent
**Why it happens:** Trying to maximize registrations, not understanding GDPR/privacy laws
**How to avoid:**
- Checkbox **must default to unchecked**
- "Accept" and "Reject" buttons must have equal visual weight (same size, color saturation)
- Link to T&C text, make it readable (not walls of legal text)
- Separate consent for different purposes (if collecting multiple data types)
- Store timestamp of acceptance in database
**Warning signs:** Privacy audit fails, users complain about deceptive UI, GDPR violation fines

### Pitfall 7: Forgetting Time-of-Day Awareness in Auth
**What goes wrong:** Session expiry doesn't account for timezone, tokens expire while user is active
**Why it happens:** Assuming server time = user time, not using UTC consistently
**How to avoid:**
- Store all timestamps in UTC in IndexedDB
- Convert to user's local time only for display
- Use ISO 8601 format for dates: `new Date().toISOString()`
- Check session validity on every protected route load
**Warning signs:** Users logged out at unexpected times, session expiry bugs in different timezones

### Dark Mode Toggle Hook
```typescript
// Source: https://tailwindcss.com/docs/dark-mode
// lib/useDarkMode.ts

import { useEffect, useState } from 'react';

export function useDarkMode() {
  const [isDark, setIsDark] = useState(() => {
    // Initialize from localStorage or system preference
    if (typeof window === 'undefined') return false;
    const stored = localStorage.getItem('theme');
    if (stored) return stored === 'dark';
    return window.matchMedia('(prefers-color-scheme: dark)').matches;
  });

  useEffect(() => {
    const root = document.documentElement;
    if (isDark) {
      root.classList.add('dark');
      localStorage.setItem('theme', 'dark');
    } else {
      root.classList.remove('dark');
      localStorage.setItem('theme', 'light');
    }
  }, [isDark]);

  return { isDark, toggleDark: () => setIsDark(!isDark) };
}
```

### Session Persistence Check
```typescript
// Source: https://dexie.org/ + React auth patterns
// lib/auth.ts

import { db } from '../db/db';

export async function checkExistingSession(): Promise<boolean> {
  const session = await db.sessions
    .where('expiresAt')
    .above(new Date()) // Not expired
    .first();

  return !!session;
}

export async function createSession(userId: number, token: string, expiresIn: number) {
  await db.sessions.add({
    userId,
    token,
    expiresAt: new Date(Date.now() + expiresIn * 1000),
    createdAt: new Date(),
  });
}

export async function clearSession() {
  await db.sessions.clear();
}
```

workbox: {

    {
      // App shell - Cache First (HTML, CSS, JS)

      handler: 'CacheFirst',
      options: {
        cacheName: 'app-shell',
        expiration: {
          maxEntries: 50,

        },
      },
    },
    {
      // API requests - Network First (prefer fresh data, fallback to cache)
      urlPattern: /^https:\/\/api\.your-domain\.com\/.*/,
      handler: 'NetworkFirst',
      options: {
        cacheName: 'api-cache',
        networkTimeoutSeconds: 10, // Fallback to cache after 10s

| localStorage for auth tokens | Memory + HttpOnly cookies | Ongoing | Better XSS protection, security best practice |
| Manual service worker scripts | Workbox + vite-plugin-pwa | 2020+ | Automatic cache management, update strategies |
| Custom dark mode logic | Tailwind dark mode + CSS variables | 2021+ | Built-in support, no flash, system preference sync |
| Manual IndexedDB API | Dexie.js | Ongoing | Promise-based, simpler API, 100k+ sites use it |

**Deprecated/outdated:**
- **Create React App (CRA):** No longer recommended by React team, superseded by Vite, Next.js, or Remix
- **Class components:** Still supported but hooks are preferred for new code
- **Separate @radix-ui packages:** shadcn/ui new-york style now uses unified `radix-ui` package (Feb 2026)
- **Browse-wrap T&C acceptance:** GDPR/CPRA require affirmative action (clickwrap), pre-checked boxes are non-compliant

## Open Questions

1. **Backend Architecture for Password Auth**
   - What we know: Passwords must be hashed server-side with bcrypt (12+ rounds), sent over HTTPS
   - What's unclear: Phase 1 focuses on frontend - do we mock auth for now, or build a minimal Node.js backend?
   - Recommendation: **Phase 1 can mock auth with Dexie.js only** (store email/password locally for demo), build real backend in Phase 2 when onboarding requires server validation. Flag as temporary in docs.

2. **Hosting Platform Choice**
   - What we know: Netlify and Vercel both support PWAs, auto-HTTPS, auto-configure service worker headers
   - What's unclear: Which aligns better with future backend needs (Groq API in Phase 4)?
   - Recommendation: **Start with Vercel** - better Edge Functions support for future API routes, generous free tier, Vite deployment is one command (`vercel`).

3. **Neuroscience Color Palette - Scientific Sources**
   - What we know: Blue/green calming, warm tones energizing, pink reduces stress (WebSearch findings)
   - What's unclear: Specific HSL values backed by published neuroscience studies
   - Recommendation: **Start with evidence-based hues from search results**, document sources in theme.css comments, validate with user testing in Phase 5 (dashboard). Adjust based on feedback.

4. **Progressive Enhancement vs Offline-First**
   - What we know: App shell architecture caches UI, IndexedDB stores data
   - What's unclear: Should Phase 1 work 100% offline (no backend), or is partial offline (cached shell, network for auth) acceptable?
   - Recommendation: **Phase 1 targets partial offline** - app shell loads offline, login requires network (mocked or real backend). Full offline sync comes in Phase 7 (notifications + tracking).
